# Профилирование 1 ноября 2026

Запись сделана через React `<Profiler onRender>` и браузерный
`PerformanceObserver` для `longtask`: Chrome 156, Windows, Vite development,
StrictMode, без CPU/network throttling. Это запись коммитов всего App,
не экспорт расширения React DevTools и не Chrome Performance trace.
`actualDuration` измеряет рендер React, а не полную задержку от ввода до кадра.
Документация API: https://react.dev/reference/react/Profiler.

## Каталог

Прогретый каталог, последовательная замена строки поиска. Основные коммиты:

| Запрос | До, мс | После, мс |
|---|---:|---:|
| жим | 24.8 | 19.2 |
| присед | 25.9 | 23.4 |
| подтягивания | 29.2 | 19.5 |
| squat | 29.6 | 21.4 |
| очистка поиска | 21.6 | 22.7 |
| Медиана | 25.9 | 21.4 |

Один сравнительный прогон: ориентировочно −17% по медиане, но этого
недостаточно для статистического вывода или обещания ускорения production.
После каждого запроса проверялись видимые результаты. В базовой записи
был также коммит с actualDuration=0; он не включён в таблицу основных коммитов.
В обеих записях прогретого поиска long tasks отсутствовали. При первом
открытии каталога до правок была одна задача 50 мс; холодную загрузку после
правок сопоставимо не измеряли.

Изменения:

- Закрытая панель расширенных фильтров больше не строит JSX десятков
  переключателей и не вызывает их переводы при каждом поиске.
- Объект URL-фильтров сохраняет ссылку, пока параметры не изменились:
  посторонние рендеры не инвалидируют `useDeferredValue` и `useMemo` списка.

Полная запись после изменений: [catalog-after.json](catalog-after.json).

## Тренировка

Отдельный чистый origin `127.0.0.1:53791`: свободная тренировка,
3 упражнения × 3 подхода, пустая история. Ввод 12 повторов вместо 10:
11.3 мс. Отметка подхода и запуск отдыха: 12.9 мс. В следующем фрагменте
примерно 10 секунд обновления отдыха обычно занимали 0.6–1.2 мс, обновления
прошедшего времени — 0–0.2 мс. Long tasks не было.

Изоляция таймеров и memo карточек уже работают; приоритетной проблемы здесь
не видно. Это не нагрузочная проверка большой истории или старого телефона.

## Первоначальные кандидаты

- Поисковый индекс создаётся заново при монтировании каталога/пикера.
  `node scripts/perf-audit.mjs` дал медиану построения 8.48 мс для 968
  упражнений, сами запросы — 0.06–0.17 мс. Стоит отдельно сравнить повторное
  открытие пикера с общим кешем индекса по данным и языку. Node-замер не
  доказывает стоимость в браузере.
- Стартовые JS/CSS и modulepreload-ресурсы сборки: 468388 байт,
  147989 байт gzip. Чанк с именем `createLucideIcon` — 111164 байта / 36722 gzip.
  Это кандидат для анализа графа импортов и загрузки на медленной сети,
  а не подтверждённый bottleneck.
- Для решений о загрузке, layout/paint и мобильном INP нужна отдельная
  production-запись Chrome Performance с throttling. Встроенный браузер
  текущей сессии не предоставляет запись такого trace.

## Повторная проверка кандидатов

### Подтверждено: индекс пересобирался при каждом открытии

Три открытия прогретого каталога и три открытия прогретого выбора упражнений
в том же браузере. Дополнительно записывались `performance.measure` вокруг
построения индекса: `fitnoss:search-index:build`. Это позволяет отделить
построение индекса от общего рендера страницы.

| Сценарий, 3 открытия | Построений до → после | Медиана суммарного рендера открытия до → после |
|---|---:|---:|
| Каталог | 6 → 0 | 45.1 → 19.9 мс |
| Выбор упражнений | 6 → 0 | 44.4 → 20.3 мс |

Одно построение занимало 10–12.5 мс. Шесть вместо трёх — повторный вызов
`useMemo` в StrictMode; production раньше строил индекс один раз при каждом
монтировании. В выборе упражнений до правки было две long tasks на 51 и
52 мс, после правки — ни одной в этом коротком фрагменте.

Исправление: `getSearchIndex` использует общий WeakMap по снимку каталога и
переиспользует индекс между каталогом, выбором и заменой упражнения. Для
каждого снимка хранится только последняя пара словарей en/local. При смене
любой пары или данных строится новый индекс. Старый каталог может быть
собран GC; кеш не накапливает индексы всех языков. Строки поиска и фильтры
не меняют индекс.

Три регрессионных теста проверяют переиспользование, появление переводов,
смену языка, изменение английских названий и замену каталога. В браузере
проверены: русский поиск в выборе, поиск `pistol` в замене и применение
результата; RU → EN с `squat` (61 результат) → RU с `присед` (62 результата).

[Сводка записанных длительностей](remount-comparison.json). Это небольшой
dev-прогон, не обещание ускорения production в два раза. Каталог до правки
записывался без активной тренировки, после — с пустой тестовой тренировкой и
баннером продолжения; прямой счёт построений индекса от этого не зависит.
Выбор упражнений в обоих случаях открывался из пустой активной тренировки.

### Не подтвердилось: лишняя загрузка иконок

Проверен состав production-чанков через `generateBundle` Vite. В чанке
`createLucideIcon` 37 модулей; основная часть — i18next, tailwind-merge,
React Router и React. Lucide занимает 7002 из 214631 байта отрендеренного
исходного кода **до минификации**. Это не 111 КБ иконок и не признак загрузки
всего набора Lucide. Исходное предположение по имени файла было неверным.
Конфигурация чанков и импорты иконок оставлены без изменений.

После исправления: `npm test` — 116 тестов, `npm run build` — успешно;
проверка precache — успешно. Рекордер и метки построения индекса отсутствуют
в production-assets. Для повторения замера прогреть каталог, нажать Reset,
трижды уйти на главную и обратно; аналогично трижды открыть/закрыть выбор
упражнений. Snapshot теперь включает `searchIndexBuilds`.

## Воспроизведение

1. `npm run dev`, открыть `http://127.0.0.1:5173/?profile#/exercises`.
2. Прогреть каталог, раскрыть React Profiler и нажать Reset.
3. Сменять запросы, дожидаясь результатов. Snapshot останавливает запись
   и выводит JSON. Reset очищает буфер и начинает новую запись.
4. Download JSON сохраняет текущую запись локально. Для нового запуска
   после изменения хуков полностью перезагрузить страницу, чтобы исключить HMR.

Рекордер подключается только в dev при `?profile`, имеет лимит 5000 коммитов,
не отправляет данные и исключается из production-сборки. Запись содержит
hash маршрутов, включая запросы и потенциальные share payload: просматривать
JSON перед передачей другим людям.

Проверено: открытие фильтров, выбор «Грудь» → 96 упражнений, закрытие панели;
поиск на русском и английском; выбор трёх упражнений, ввод повторов и отметка
подхода. `npm test`: 29 файлов, 113 тестов. `npm run build`: успешно.
Проверка precache через `scripts/perf-audit.mjs`: пропущенных ресурсов нет.
В production-assets нет рекордера.
