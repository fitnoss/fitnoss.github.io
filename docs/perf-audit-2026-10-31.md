## Находки по приоритету

P1 ниже означает первую очередь оптимизации; P2 — следующую. Это приоритет работы, а не утверждение о доказанном нарушении Web Vitals.

### 1. P1 — старт загружает полные инструкции, в том числе для закрытой панели

**Подтверждение:** [ProgramsPage.tsx:89](../src/features/programs/ProgramsPage.tsx#L89) всегда монтирует `NewProgramSheet`; [NewProgramSheet.tsx:24](../src/features/programs/NewProgramSheet.tsx#L24) вызывает `useExercises()` независимо от `open`. Сам `Sheet` скрывает содержимое, но не останавливает хуки компонента-родителя. [exercise/store.ts:36](../src/entities/exercise/store.ts#L36) скачивает метаданные и весь английский текст; [строка 53](../src/entities/exercise/store.ts#L53) начинает русский текст только после завершения core Promise.

Для русской локали это **1 969 720 байт JSON** (метаданные + en/ru инструкции), или около **344,62 КБ gzip** по локальному сжатию. На пустой главной эти данные нужны закрытому диалогу, а не видимому содержимому. Готовность каталога также ждёт полных текстов обоих языков.

**Исправление:** монтировать содержимое создания программы при открытии; отделить названия и краткие метаданные от инструкций; получать детали при открытии упражнения. Если сохранять полные файлы, хотя бы запрашивать язык параллельно с core и дедуплицировать Promise по языку. Сейчас общий Promise есть только для core: несколько одновременных потребителей могут запрашивать один локальный файл отдельно.

Эксперимент с `{slug: {name}}` уменьшает русский файл с 182,55 до 17,21 КБ gzip — примерно **91%** для этого файла. Это потенциальное сокращение критических данных, не измеренное ускорение страницы.

**Проверка результата:** при первом открытии пустой главной приложение не запрашивает тексты упражнений; при открытии каталога в Network нет последовательного ожидания en → ru. Запросы SW следует учитывать отдельно.

### 2. P1 — секундный таймер перерисовывает всю активную тренировку

**Подтверждение:** [WorkoutPage.tsx:31](../src/features/workout/WorkoutPage.tsx#L31) обновляет `now` каждую секунду, а [строка 51](../src/features/workout/WorkoutPage.tsx#L51) использует этот хук в `ActiveWorkout`, который строит весь список. `ExerciseCard` не мемоизирован; при каждом таком рендере [ExerciseCard.tsx:48](../src/features/workout/ExerciseCard.tsx#L48) заново выполняет `lastSets(history, ...)`. Для давно не использовавшихся упражнений это проход по большой части истории.

Кроме того, [ExerciseCard.tsx:45](../src/features/workout/ExerciseCard.tsx#L45) и [WorkoutPage.tsx:46](../src/features/workout/WorkoutPage.tsx#L46) подписываются на весь session store ради действий. Поэтому любое изменение подхода или состояния отдыха оповещает все карточки. Подписки `useExercises()` и `useSettings()` также широкие.

**Исправление:** вынести elapsed clock в маленький компонент заголовка; выбирать действия и данные Zustand селекторами; мемоизировать карточки со стабильными props; мемоизировать предыдущие результаты по `history`, коду и типу повторов. Установка одного `memo` не устранит широкую подписку на store.

**Проверка результата:** в React Profiler на тренировке из 12 упражнений ожидание 30 секунд обновляет часы, но не коммитит все карточки; правка одного подхода не рендерит остальные карточки. Это критерий будущей проверки, а не снятый профиль.

### 3. P2 — каждое изменение подхода сериализует всю историю

**Подтверждение:** [session/store.ts:236](../src/entities/session/store.ts#L236) использует стандартный `persist` без собственного storage/разделения данных. Установленный Zustand в `node_modules/zustand/esm/middleware.mjs` вызывает `JSON.stringify` и `localStorage.setItem` после каждого `set`. [toggleSet:157](../src/entities/session/store.ts#L157) вызывает `updateSet`, затем при обычном запуске отдыха ещё `startRest`: две записи полного состояния на одно действие. `NumberInput` передаёт изменение на каждом принятом символе.

| Тренировок в синтетической истории | JSON, UTF-8 | Медиана stringify | p95 stringify |
|---:|---:|---:|---:|
| 100 | 163,37 КБ | 0,54 мс | 1,36 мс |
| 500 | 810,57 КБ | 2,67 мс | 3,50 мс |
| 1 000 | 1 619,57 КБ | 5,35 мс | 6,46 мс |

Таблица измеряет только сериализацию похожего состояния в Node. Запись localStorage, React и мобильный CPU в неё не входят. UTF-8 размер не равен учёту квоты localStorage; число UTF-16 code units сохранено в JSON-результате.

**Исправление:** хранить активную тренировку отдельно от архива, записывать архив при завершении/редактировании истории. При росте архива — IndexedDB с записями по тренировкам. Объединить обновление подхода и запуск отдыха в одну транзакцию store. Простое добавление `partialize` с теми же данными не устранит повторные записи.

**Проверка результата:** инструментировать storage; изменение подхода не сериализует архив, завершение сохраняет новую тренировку. Проверить перезагрузку/восстановление активной тренировки и существующие тесты истории.

### 4. P2 — большинство маршрутов входит в стартовый граф JS

**Подтверждение:** [App.tsx:6](../src/app/App.tsx#L6) статически импортирует каталог, редактор программы, тренировку, журнал, настройки и About. Лениво подключаются только калькуляторы и прогресс упражнения. `dist/index.html` загружает основной JS и preload `segmented-*.js`; считать стартом только основной файл нельзя. Совокупный стартовый JS — **569,09 КБ**, gzip **178,95 КБ**.

**Исправление:** оставить главную и каркас стартовыми, использовать route-level lazy для редактора, тренировки, журнала, каталога и прочих вторичных экранов. Лениво монтировать тяжёлое содержимое диалогов. Существующая Suspense-граница в Layout позволяет сохранить навигацию во время загрузки; добавить заметный fallback для содержимого.

**Проверка результата:** сравнить JS, подключённый из HTML, и Coverage на пустой главной; не ориентироваться на названия чанков. Проверить переходы и прямые hash-ссылки. Размер экономии до такой сборки не установлен.

### 5. P2 — анимации изображений работают для всех смонтированных карточек

**Подтверждение:** [ExerciseImage.tsx:22](../src/shared/components/ExerciseImage.tsx#L22) по умолчанию анимирует два кадра и создаёт отдельный `setInterval` на 1,1 с. В каталоге проверены 22 `<img>` на первом экране. Виртуализация ограничивает число карточек, но включает overscan; в списке тренировки все упражнения смонтированы. Остановка по пересечению viewport и `document.hidden` отсутствует. `loading="lazy"` откладывает загрузку картинки, но не выполнение таймера React.

**Исправление:** для миниатюр использовать один кадр или запускать анимацию только у видимых упражнений; останавливать таймер при скрытии страницы. Сохранить анимацию в открытой технике упражнения. У первого большого кадра на странице упражнения рассмотреть `eager`/`fetchPriority="high"`; второй кадр не должен конкурировать с первым. Сейчас `lazy` установлен для всех изображений, включая главное.

**Проверка результата:** при скрытой вкладке нет анимационных обновлений; вне viewport нет активных таймеров. Приоритет большого кадра оценить по фактическому LCP на мобильном устройстве — сейчас LCP-элемент не измерен.

### 6. P2 — история растёт без ограничения DOM

**Подтверждение:** [JournalPage.tsx:131](../src/features/journal/JournalPage.tsx#L131) выводит `history.map(...)` целиком, в отличие от виртуализированного каталога. Каждый `SessionRow` рассчитывает количество подходов и тоннаж. Расчёты records/mine также выполняются при входе независимо от выбранной вкладки.

**Исправление:** пагинация или виртуализация истории, расчёты вторичных вкладок по необходимости. Выбирать по профилю на 500–1 000 тренировок; ранняя сложная индексация пока не обоснована.

**Проверка результата:** число DOM-узлов истории ограничено размером страницы/viewport; измерить вход в журнал, прокрутку и смену вкладок с синтетической историей.

## Ограничения офлайн-режима для оптимизации

[vite.config.ts:50](../vite.config.ts#L50) precache-ит все JS, CSS, шрифты (кроме flags), JSON данных и обе локали. Разделение маршрутов само по себе уменьшит стартовое выполнение JS, но SW по-прежнему скачает ленивые чанки для офлайна. Разделение текстов аналогично не сократит общий объём первой установки, если всё продолжит precache-иться.

Поэтому отдельно оценивать время до полезного экрана и время готовности офлайна. Не убирать precache без проверки заявленного поведения: маршруты, локализация и данные должны оставаться доступны после первой полной установки. Поэтапное скачивание может изменить гарантию офлайна и требует явного продуктового решения. `registerType: "prompt"` управляет обновлением, а не отключает первоначальную установку SW.

Ещё одна задержка по исходникам: [main.tsx:22](../src/main.tsx#L22) не монтирует React до завершения i18n; [i18n/index.ts:41](../src/shared/i18n/index.ts#L41) сначала получает список языков, затем UI-переводы. Это последовательные сетевые стадии до первого содержимого приложения. Рассмотреть включение списка языков в сборку и лёгкого локализованного fallback. Без измеренного waterfall влияние в миллисекундах не определено.
